# Contributing

## Adding a component

1. `pnpm --filter @pearpages/pulp-react scaffold Name Category` creates the five files,
   a component token file, and registers the entry point. The category is a kind
   (Typography, Layout, Actions, Forms, Navigation, Overlays, Feedback, Data, Utilities):
   what a consumer reaches for, never when it was built. (Coding agents: the
   `add-component` skill runs the same script.)
2. Fill `tokens/component/<name>.json` with references to the **semantic**
   layer only. Run `pnpm build:tokens` and commit the generated CSS.
3. Write the component. Rules that CI enforces:
   - every colour, radius, font and shadow is a `var(--…)`;
   - no `style` prop, no CSS-in-JS, no utility classes;
   - state on the DOM as `data-*` attributes;
   - variants as union types, never boolean props that conflict;
   - `ref` is a normal prop; `asChild` for composition where it makes sense;
   - the component's JSDoc carries `@status` (`experimental | stable | deprecated`),
     `@category` and an `@accessibility` paragraph, plus `@do` / `@dont` bullets (one per
     line). The manifest build fails without status, category and accessibility. That
     JSDoc *is* the docs page: the Docs tab, the Status page, the sidebar and coding agents
     all read it through the manifest, so nothing is written twice. The story title is
     `Components/<Category>/<Name>`; the dist smoke test fails when it disagrees with the tag.
4. Tests: behaviour with Testing Library, an `axe` check for every state.
5. Stories: one per variant, a `play` for anything interactive, and the four
   brand × scheme matrix stories. Stories run as tests in a browser and fail
   on a11y violations. No `parameters.docs.description`: the Docs page renders
   the JSDoc. Matrix stories are tests and are left off the Docs page.
6. `pnpm build` regenerates the component manifest from your prop types and
   JSDoc; `pnpm check:size` checks the entry against its bundle budget
   (`packages/react/.size-limit.js`, a default for leaf entries plus overrides).
7. `pnpm changeset` to describe the change for the changelog.

## Checklist before a PR

```
pnpm check:generated && pnpm lint && pnpm typecheck && pnpm test && pnpm build && pnpm test:dist && pnpm check:package && pnpm check:size
```

## Versioning and deprecation

- Semantic versioning per package, driven by changesets.
- Removing or renaming a token, a prop, or a `data-*` attribute is a **major**.
- Anything removed stays for one major with a deprecation note in the
  changelog and, where the change is mechanical, a codemod.
- Brands never break: adding a semantic token means adding it to every brand
  file, and the token tests fail otherwise.

## Guardrails that watch vendors

- `dialog/Dialog.vendor.test.ts` reads the installed `@pearpages/modals` stylesheet and finds
  every component stylesheet that maps a `--modal-*` variable (Dialog's colours and spacing,
  Sheet's sizes). It fails if one maps a name the vendor no longer declares, or drops below its
  lower bound, so a vendor rename cannot silently unstyle Dialog or Sheet. A new stylesheet
  that maps vendor variables gets a bound in that file.
- The dist smoke test asserts every vendor (`@pearpages/modals`, `@floating-ui/react-dom`,
  `react-aria-components`) is imported, never bundled.

## Known limitations

- `Field` registers its description and error in a layout effect, so server-rendered HTML has
  no `aria-describedby` until hydration. A test in `Field.test.tsx` pins the gap; when it
  starts failing, the limitation is gone.

## Releasing

Tag `vX.Y.Z` on `main` after `pnpm version-packages` has landed. The publish
workflow packs each package with `pnpm pack` (so `workspace:*` becomes a real
range) and publishes through npm trusted publishing, no tokens involved.
