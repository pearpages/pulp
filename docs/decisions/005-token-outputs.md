# 005. One `tokens.css`, plus two views of the semantic tier for Tailwind and React Native

Date: 2026-09-19 (group 10). Status: accepted for the two new outputs; the per-component split
is deferred, with the trigger below. For Pere to confirm.

## Context

`@pearpages/pulp-tokens` shipped two files: `tokens.css` (every tier, both brands, `light-dark()`
pairs) and `tokens.json` (the same, as data). Two questions had been waiting for a consumer.

**Is one stylesheet the right shape?** Measured on 2026-09-16, `tokens.css` was 46.4 kB raw, of
which **component tokens are 66%** (30.8 kB) and the whole bitepals brand block 7.8 kB.

- Splitting **per brand** is the wrong cut. It saves at most 1.4 kB brotli for a one-brand
  consumer, costs about 760 B for anyone loading both, and breaks two things the system promises:
  brands nest (`data-brand` on any element) and a brand is a token swap at run time, which is how
  the Storybook toolbar and a themed section of a page work. Both need every brand in the sheet.
- Splitting **per component** (each `--button-*` block shipped next to `button.css`) is the cut
  that would pay, since a consumer then carries only the tokens of what it renders.

**What about consumers that are not a browser stylesheet?** bitepals, the second consumer, has
two: a Next.js app on Tailwind v4 (on its way out of Tailwind, but not there yet), and an Expo
app on NativeWind, where there is no cascade, no `light-dark()` and no `rem`. Its own
`packages/tokens` produced a `tailwind-tokens.cjs` of `{ colors, radius, themeVars }` for that,
read by `tailwind.config.js` and by a theme provider that calls NativeWind's `vars()`.

## Decision

1. **`tokens.css` stays one file.** The per-brand split is rejected for the reasons above. The
   per-component split is **deferred**: it touches `build.mjs`, the component→semantic test, the
   dist smoke test, every `*.css` entry and the docs, and no consumer has asked for the bytes yet.
2. **`./theme.css`**: a Tailwind v4 block over the **semantic tier only** (colour, radius, shadow,
   font family), so utilities are the system's vocabulary (`bg-surface-base`, `rounded-control`)
   and never a primitive or a component token. It is written as

   ```css
   @theme inline reference { --color-surface-base: var(--color-surface-base); … }
   ```

   `inline` makes a utility emit `var(--color-surface-base)` itself, so it follows `data-brand`
   and `data-scheme` at run time. `reference` is not optional: compiled with tailwindcss 4.3.0,
   plain `@theme inline` still writes `:root { --color-surface-base: var(--color-surface-base) }`
   into Tailwind's `theme` layer. That layer is declared after pulp's, so it wins over
   `@layer tokens`, and the declaration is a cycle: the token becomes invalid and everything
   painted with it disappears. (bitepals used the same-name pattern safely only because its own
   variables were unlayered.) With `reference` Tailwind emits no variables at all.
3. **`./native`**: per brand, `{ colors, radius, space, themeVars: { light, dark } }`. Names are
   `var(--…)` references nested by path (`colors.surface.base`), which is what a Tailwind config
   wants; `themeVars` holds what those variables resolve to per scheme as literals (hex, px), which
   is what `vars()` wants. Spacing is resolved through the brand's `space.unit`, so density
   survives (`--space-4` is 16 px in pulp and 17.92 px in bitepals). Shipped as ESM and as
   CommonJS under a `require` condition, because Metro and a Tailwind v3 config load it with
   `require`. `tokens.json` already carried resolved `light` / `dark` values; nothing was added to it.

Both files are generated by `scripts/build.mjs` (`scripts/outputs.mjs`), committed, and covered by
the same drift check as `tokens.css`.

## Consequences

- PRINCIPLES §4 still holds for what pulp itself ships: no utility classes in the library.
  `theme.css` is a bridge for a consumer that has Tailwind, not an endorsement of it.
- Shadows, type sizes, motion and z-layers are not in `native`: React Native has no `box-shadow`
  string, and the rest has had no consumer. Add a group when one asks, not before.
- A semantic token added later appears in both outputs with no further work; the tests check that
  every name `native` exposes has a value in both schemes, and that `theme.css` references nothing
  outside the semantic tier.
- Tailwind is not a dependency of this repo, so the `reference` behaviour is pinned by a test on
  the text of the file, not by compiling it. The group 9 consumer fixture is where a real compile
  belongs.

## Revisit when

- A consumer measures `tokens.css` as a cost that matters (a landing page rendering three
  components): then do the per-component split.
- Tailwind changes what `@theme inline reference` emits: re-run the compile and adjust.
- The Expo app needs shadows or type sizes from the system: extend `native`.
